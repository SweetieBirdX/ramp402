## 1.1 Units and type rules (apply everywhere)

- **All amounts are integer stroops.** No decimals anywhere — not in the DB, not in API payloads,
  not in contract calls. Only React components converting for display do `stroops / 10_000_000`.
- **`endpoint_id` is a `u64`**, assigned by the contract itself inside `register_endpoint` from an
  incrementing counter. Neither the frontend nor the gateway invents one. In SQLite's
  `endpoints.id TEXT PRIMARY KEY` column, store the decimal string form of that u64 (`"1"`, `"2"`,
  …) — the schema does not change, only the content rule.
- **`proxy_slug`** is a separate, human-readable, URL-safe identifier generated by the gateway
  (e.g. `nanoid(8)`). It is never confused with `endpoint_id`: one is the on-chain identity, the
  other is the URL identity.
- **Addresses** travel everywhere as classic Stellar `G…` strings. Conversion to the Soroban
  `Address` type happens inside the gateway only; frontend and DB always see strings.
- **Status enums** (`calls.status`, `withdrawals.status`) are exactly:
  `paid | upstream_failed | refunded` and `pending | completed | failed`.
  A new status name must be added to this document first.
- **Errors**: the gateway returns `{ "error": "<machine_code>", "message": "<human text>" }` with
  the appropriate HTTP status. Machine codes used across components:
  `missing_budget_header`, `budget_exceeded`, `endpoint_not_found`, `upstream_failed`,
  `unauthorized`, `anchor_error`, `not_implemented`.

## 1.2 `ramp_ledger` contract — exact storage and signatures

**Persistent storage (TTL must be extended on every write):**

```
NextEndpointId: u64                            → counter, +1 on every register_endpoint
Endpoints:      Map<u64, EndpointInfo>         → EndpointInfo { seller: Address, price: i128 }
Budgets:        Map<(Address, u64), BudgetEntry>
                                               → key = (agent, endpoint_id)
                                               → BudgetEntry { allocated: i128, spent: i128 }
SellerBalances: Map<Address, i128>             → settle() credits 99% here, withdraw() zeroes it
TreasuryTotal:  i128                           → cumulative 1% platform fee
```

**Functions — signatures are fixed:**

```rust
// 1) Called by the seller with their own require_auth(). The contract generates and returns the new endpoint_id.
fn register_endpoint(env: Env, seller: Address, upstream_price: i128) -> u64;
// event: EndpointRegistered { id, seller, price }

// 2) Called by the gateway's single "operator" keypair (operator.require_auth()). The agent does NOT sign.
// On the FIRST call for an (agent, endpoint_id) pair the budget parameter is read and frozen.
fn record_call(env: Env, operator: Address, agent: Address, endpoint_id: u64, budget: i128);
// panic: SpendingLimitExceeded  if spent + price > allocated
// panic: EndpointNotFound       if endpoint_id does not exist

// 3) Called by the gateway's operator keypair. 1% to treasury, 99% credited to SellerBalances[seller].
fn settle(env: Env, operator: Address, endpoint_id: u64, amount: i128);
// event: FeeSettled { endpoint_id, seller_share, treasury_share }

// 4) Called by the seller with their own require_auth(). Zeroes SellerBalances[seller], returns the amount.
fn withdraw(env: Env, seller: Address) -> i128;
// event: Withdrawn { seller, amount }

// 5) View function (no auth) — backs the gateway's GET /api/balance.
fn get_balance(env: Env, seller: Address) -> i128;

// 6) View function — backs the gateway's price/limit checks.
fn get_endpoint(env: Env, endpoint_id: u64) -> EndpointInfo;
```

**There are no sessions.** The budget is defined on an agent's **first call** to an endpoint and is
fixed from then on. The grouping key is `(agent address, endpoint_id)`. There is no `session_id`,
no `/session` route, and no state the agent has to carry.

**Rounding rule for `settle`:** integer arithmetic only. `treasury_share = amount / 100` (integer
division), then `seller_share = amount - treasury_share`. Rounding must never favour the payer or
the seller over the treasury.

**Minimum `cargo test` set (six tests, all must be green):**

1. Calling `register_endpoint` twice returns two different ids (counter increments correctly)
2. `record_call` freezes `budget` on the first call; on the second call the parameter is ignored
   — passing a *larger* budget later must NOT raise the limit
3. Exceeding the budget panics with `SpendingLimitExceeded`
4. `settle` splits 1% / 99% correctly, and rounding never favours the user
   (amount 5_000_000 → treasury 50_000, seller 4_950_000; also test a non-divisible amount)
5. An unauthorised `withdraw` (wrong signer) panics
6. `SellerBalances` is zero after `withdraw`

**Authorisation model:**

| Function | Signer | Why |
| --- | --- | --- |
| `register_endpoint` | seller | endpoint ownership stays with the seller |
| `record_call` | gateway operator keypair | the agent must not sign a second time on every call |
| `settle` | gateway operator keypair | same reason; it only updates the ledger |
| `withdraw` | seller (own balance only) | the only authority that moves money stays with the seller |

This contract **never holds or transfers tokens**. It is a ledger. The actual USDC movement happens
off-chain from the platform pool account. That is a documented architectural decision, not an
oversight.

## 1.3 REST API contract (gateway ↔ frontend)

Base URL: the gateway's `PORT` from `gateway/.env`; the frontend calls it via
`NEXT_PUBLIC_GATEWAY_URL`. Seller endpoints require `Authorization: Bearer <privy_access_token>`;
the gateway verifies it with the Privy server SDK and resolves `privy_user_id → stellar_address`
from the `sellers` table.

### Seller onboarding

- `POST /api/sellers/bootstrap` — no body, auth header only. On first login: insert a row in
  `sellers` if absent, then **fund the address automatically via Friendbot**. Returns
  `{ seller_id, stellar_address, funded: true }`. The frontend calls this once, immediately after
  login. Must be idempotent.

### Endpoint registration — two-step

`register_endpoint` needs the seller's signature and only Privy (client-side) can produce it, so
the gateway builds an unsigned transaction and the frontend returns it signed.

- `POST /api/endpoints/prepare` — body `{ upstream_url: string, price_stroops: number }`
  → `{ unsigned_xdr: string, draft_id: string }`
- *(the frontend has Privy sign that XDR)*
- `POST /api/endpoints/submit` — body `{ draft_id, signed_xdr }` → the gateway submits to the
  network, waits for the result, **reads the `endpoint_id` returned by the contract**, writes the
  row into `endpoints` (id = decimal string of `endpoint_id`, `proxy_slug` generated by the
  gateway) → `{ endpoint_id, proxy_slug, upstream_url, price_stroops }`

### Withdrawal — same two-step pattern

- `POST /api/withdraw/prepare` → `{ unsigned_xdr, draft_id }`
- `POST /api/withdraw/submit` — body `{ draft_id, signed_xdr }` → calls the contract's `withdraw`,
  then kicks off the SEP-10 / SEP-38 / SEP-12 / SEP-6 + classic payment flow **in the background**
  → returns `{ withdrawal_id, status: "pending" }` immediately
- `GET /api/withdrawals/:id` — for polling:
  `{ status: "pending"|"completed"|"failed", anchor_tx_id?, external_transaction_id? }`

### Read endpoints

- `GET /api/endpoints` → the seller's own endpoint list (from SQLite). Never another seller's rows.
- `GET /api/balance` → reads the contract's `get_balance` view → `{ balance_stroops }`.
  The chain is the source of truth — do not sum the `calls` table.
- `GET /api/calls?endpoint_id=` → call log from SQLite, newest first, including `status` and
  `tx_hash`. Verify the endpoint belongs to the authenticated seller.
- `GET /health` → `{ ok: true }` (used by `scripts/verify-e2e.ts` and `scripts/preflight.ts`)

### Agent side — no seller auth; this is the x402 protocol itself

- `GET /proxy/:proxy_slug` — 402 → retry with `X-PAYMENT` → 200.

  On the **first** call for a given `(agent, endpoint)` pair the header
  `X-Agent-Budget: <stroops>` is **mandatory**; if it is missing, return `400` with
  `{ "error": "missing_budget_header" }`. There is no default budget. On subsequent calls the
  header is ignored if present.

  Budget exceeded → `403` with `{ "error": "budget_exceeded" }` plus the rejected transaction hash.

  Upstream returned non-2xx / timed out → write a `calls` row with status `upstream_failed`, do
  **not** call `settle`, return `502` with `{ "error": "upstream_failed" }`.

## 1.4 SQLite schema

Database file: `ramp402.db`. It and `*.db-wal` / `*.db-shm` are gitignored; `schema.sql` is
committed. The schema is idempotent (`IF NOT EXISTS`) and is executed on startup.

```sql
CREATE TABLE IF NOT EXISTS sellers (
  id TEXT PRIMARY KEY,
  privy_user_id TEXT NOT NULL,
  stellar_address TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS endpoints (
  id TEXT PRIMARY KEY,
  seller_id TEXT NOT NULL REFERENCES sellers(id),
  upstream_url TEXT NOT NULL,
  proxy_slug TEXT NOT NULL UNIQUE,
  price_stroops INTEGER NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS calls (
  id TEXT PRIMARY KEY,
  endpoint_id TEXT NOT NULL REFERENCES endpoints(id),
  agent_address TEXT NOT NULL,
  amount_stroops INTEGER NOT NULL,
  status TEXT NOT NULL, -- paid | upstream_failed | refunded
  tx_hash TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS withdrawals (
  id TEXT PRIMARY KEY,
  seller_id TEXT NOT NULL REFERENCES sellers(id),
  amount_stroops INTEGER NOT NULL,
  anchor_tx_id TEXT,
  status TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

Rules:

- Always use `?` placeholders. Never build SQL by string concatenation.
- Prepare statements once and cache them; do not call `prepare()` per request.
- `endpoints.id` holds the decimal string form of the contract's `u64` endpoint_id (see §1.1).
- SQLite is a cache for the UI. The chain is the source of truth for balances — if the database is
  lost, balances are unaffected and the cache can be rebuilt.

## 1.5 Anchor rules (gateway)

These come from known failure modes. Each one has cost someone a debugging session.

- Everything — the transfer server URL, the USDC issuer, the limits — is read from the anchor's
  `stellar.toml` via its home domain. **Hardcode nothing**; the mainnet issuer is different.
- The payment to the anchor is a **classic payment operation with `memo_type: id`** and the exact
  memo the anchor returned. Never a contract call, never a text memo — both fail to match and the
  transaction hangs unresolved.
- The SEP-12 KYC form is generated from the `fields` map the anchor **returns**. Never hardcode the
  field list.
- SEP-38 quotes are single-use and expire in 15 minutes.
- If the SEP-10 JWT expires (401), re-authenticate automatically and retry once.
- The 1 USDC withdrawal limit is a **lower bound, not a cap**. Reject amounts below it with a clear
  message; never silently clamp to it.
- If a trustline is missing, the resulting `pending_trust` / claimable-balance state must be
  surfaced in the withdrawal status so the UI can show a claim path.
- Code that only works against the mock anchor (e.g. `simulate-bank-transfer`) is isolated in its
  own module and marked `// MOCK ANCHOR ONLY`.
